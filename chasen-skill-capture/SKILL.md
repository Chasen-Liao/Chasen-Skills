# 技能沉淀与分流

## 触发与去重

完成并**经过验证**的**可复用多步工作流**、用户要求记住/写成技能、或同类活重复出现时当场沉淀。

- **先迭代既有 Skill，再考虑新建**：职责重叠时直接更新现有技能，避免冗余副本。
- **精炼与单真源**：正文只写必要步骤与清晰的 `when-to-use` `description`；每条规则只保留一处权威来源并按需引用，不跨文件重复抄写。
- **运行参数外置**：助手专属配置（频道、路径、实例 ID、默认模型等）从当前助手或私有配置加载，不硬编码进通用技能。

## 公私分流与防泄露

1. **绝不整份复制本地 Skill 或 Profile 到公开仓**。
2. **分流去向**：
   - **通用可复用技能** → 已配置的公开技能库（`<public-skills-repo>`），遵循目标仓库的维护规范、版本号、`README.md` 与 PR 流程。
   - **个人身份、团队实例 ID、本机路径、设备信息、模型默认值、风格语料与角色图片资产** → **仅**写入已配置的私有仓库（configured private repository）或本地私有配置。
3. **上传私有配置前必须校验**：先实测确认目标仓库可见性为 `PRIVATE` 再写入；**未配置私有仓库时不要猜测仓库名**。
4. **公开同步前全项自检**：提交公开仓前逐项检查正文、`references/`、图片、示例、Git commit 元数据与 PR 正文，运行仓库隐私自检脚本（如 `scripts/check-public-privacy.py`），同时保留准确的法定署名与许可证声明。
5. **任何仓库均禁入**（公开与私有仓库同样适用）：密钥、凭证库（vault）、原始 memory 导出、聊天/私信记录、一次性问答与商单 brief。

## 执行边界与状态口径

- **平台优先与安全禁令**：平台执行方式与审批边界始终优先；**不把 `git push` 委托给本地执行器（如 Pi）**；已有待审 PR 时在同一 PR 分支迭代，不重复开 PR。
- **精确区分 5 类状态（严禁混报）**：
  - `local live`：仅当前平台/本地技能生效
  - `branch saved`：已提交并推送到远端分支，未建 PR
  - `PR pending`：已创建真实 PR 等待人工合并（未合并前不称已入主干）
  - `main updated`：PR 已合并入默认分支
  - `runtime loaded`：目标运行环境已实际拉取/重装加载（归档或入库不等于运行态自动生效）
- 未完成同步时如实标注「待同步」；仅在 PR 实际建立后附真实 PR 链接。

## 新建助手原则

新建助手前先联系当前已配置的设计助手（不硬编码具体名称或 ID），坚持少而精、单一职责，优先改进既有助手描述；沉淀或调整配置不隐式授权转交任务、扩大权限或新增例行任务（routines）。
