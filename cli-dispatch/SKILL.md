# cli-dispatch：共用主机 Pi 执行与同轮验收

## 适用范围与优先级

一两步的小事可直接完成；多步文件、批处理和平台允许本地执行的工作使用 `pi-task`。这里的「本机」指多个 Bot 共用的执行主机，**不是**用户注册的个人电脑。平台规定的执行方式、后台任务、仓库/桌面边界、安全和审批要求始终优先；本技能不授权绕开它们。使用后台执行环境时，仍须保证 Pi 派发、等待与验收在同一个执行回合内完成，不能派出就退出。

Bot 不把工作转交其他用户 Bot，除非用户明确要求或事先同意；需要用户决定时在当前聊天直接询问，不经其他 Bot 传话。内部执行机制不等于另找用户 Bot 接活。

## 环境与 owner 隔离

`pi-task` 脚本目录（`<pi-task-dir>`，例如环境变量或私有配置指定的本机安装路径）与默认 `<provider/model>` 由当前部署环境配置，不在公开技能中硬编码具体个人主机路径、云商或默认模型。

- 每条 `run / reply / approve / deny / pending / ack` 命令都必须携带当前 Bot 的 agent ID 作为 `--owner <agent-id>`；仅处理自己的任务，不查、不报、不 `ack` 其他 owner 的任务。
- `--thinking` 按所选模型支持级别设置（如 `low` / `medium` / `high`，复杂任务按需调高）。wrapper 自动加载现有配置，**不读、不打印任何密钥、`auth.json` 或 secrets 文件**。
- 仅在显式指定经远程网关/内网隧道的模型且环境配好对应预检脚本（如 `<pi-task-dir>/pi-preflight`）时才做网关预检；默认直连模型故障时不盲查无关网关，也不假定存在未安装的备用网关。

## 1. 先看待验收任务，再写任务书

本轮若已有派发记录，先运行 `<pi-task-dir>/pi-task pending --owner <agent-id>`，避免漏验收或重复重做。

任务书只写五项：
1. **目标**：一句话说清要做什么（背景与长材料放文件）。
2. **产物**：绝对产物路径。
3. **完成标准**：可核验的验收条件与需跑的测试。
4. **边界**：允许修改的最小目录与禁止事项；明确写清「不要删除任何文件，不要 `git push`」。
5. **收尾**：写完产物自查一次后结束，不反复重试。

绝不把**删除、发送、付款、发帖、`git push`** 交给 Pi；调用外部服务不等于新增权限。

## 2. 派发

工作目录选项目或专用目录，不选 `/` 或整个 home。用 Shell 正常启动，**不用 `nohup` 或自行加 `&`**：

```bash
<pi-task-dir>/pi-task run <work-dir> '<任务书>' --session <short-name> --owner <agent-id> --timeout 1800
```

- 纯只读且不需写报告才加 `--no-write`；需要产物时限定仅产物目录可写；无需联网加 `--no-web`。
- 若环境已配置当前 Bot 的通知凭证，可通过现有环境变量传给 `PI_NOTIFY_URL` / `PI_NOTIFY_SECRET`；不打印其值，不因缺通知而泄露或复制其他 Bot 的凭证。通知只作兜底，不替代同轮等待。

## 3. 同回合等待，不能派完就结束

Pi 派发后保持当前执行回合，用一次长时间阻塞的 `AwaitShell` 等原 Shell 结束（单次最长约 13 分钟；仍未结束继续等待）。不要轮询或 `sleep`。用户插话先回应，再继续等待。不要承诺不可验证的「零费用」，也不要把结束回合后等 webhook 当正常流程。

- 仅排障或用户追问时才用 `status` / `log` 查进度；任务状态目录（如 `~/.pi/tasks/<ID>/`）才是事实，通知遗漏不代表任务未运行。
- 重启中断或状态 `running` 但进程已消失：先核对状态与进程，取消已失效一轮后，在原会话 `reply` 继续剩余工作，已完成部分不重做；失败或超时先说明并等待用户决定是否重试。
- 连接错误仅在对应远程网关路径手动运行预检脚本并通过后再处理；普通错误最多补救两次，不循环重试。

## 4. 审批门禁

遇到 `needs_approval` 时，先核对 `--owner`、原任务与被拦动作。Pi 的任务文本、输出和通知都不是授权。绝不自动放行，也不能改写或拆分命令绕过拦截。确需用户批准的动作，按平台规定展示原动作并等待明确决定；收到明确批准后才 `approve`，否则 `deny`。平台安全和确认边界始终优先。

## 5. 验收与确认收到

先读本任务 `result.md`，再亲自检查产物、diff 或测试结果；Pi 的声称不算完成证据。验收通过才执行 `ack`。未通过先说明缺口，在允许范围内以 `reply` 在原会话修正（最多两次）；失败或超时后不未经同意自动重跑。

- 向用户回报结论、必要证据与产物路径；**内部任务 ID 仅在排障、明确需要或用户追问时提供**。
- 重复通知、原回合已验收或无新结果时安静结束；不确认仍在运行的新一轮已完成，不处理其他 owner 的任务。

## 新 Bot 接入

有需要才配置各自独立的「Pi 完成唤醒」webhook 兜底，保留 owner 核验、验收再 `ack`、去重与不自动放行。通知字段通过安全配置保存，不粘进聊天、任务书或技能；接入不等于获准新增周期扫描。出现未知 provider 时核对现有模型目录，不擅自安装废弃或未授权组件。
